# real-time-fraud-detection

A production-style fraud scoring service that turns a stream of transaction
features into **approve**, **review**, or **block** decisions. It includes local
explanations, chronological evaluation, live drift monitoring, Prometheus
metrics, a FastAPI service, and an operations dashboard.

## Read this before the metrics

The included dataset is **deterministic synthetic data**, not transactions from
a bank or payment company. The metrics demonstrate that the pipeline trains,
evaluates, serves, explains, and monitors a learnable rare-event problem. They
must not be described as expected production fraud performance.

That limitation is enforced in three places:

- the training report carries `real_bank_data: false`;
- `GET /healthz` returns the same provenance flag;
- the dashboard displays the warning beside every live result.

## What it does

```text
transaction event
      │
      ▼
feature validation ──► trained classifier ──► fraud probability
                                                │
                           ┌────────────────────┼────────────────────┐
                           ▼                    ▼                    ▼
                        approve              review               block
                           │                    │                    │
                           └──────── explanation + telemetry ───────┘
                                                │
                                                ▼
                                      live PSI drift monitor
```

- Scores a transaction through `POST /api/score`.
- Selects review and block thresholds from a validation period rather than
  tuning them on the test period.
- Explains each score using exact standardised-feature contributions from the
  deployed logistic-regression model. These are model explanations, not causal
  claims.
- Keeps a bounded in-memory operations window and reports decision counts,
  average risk, feedback, and drift.
- Calculates Population Stability Index (PSI) against the training reference.
- Exposes Prometheus counters, histograms, and gauges.
- Includes a browser dashboard with normal, suspicious, and automatic traffic
  simulation.

## Evaluation design

Transactions are ordered by event time and split **70/15/15**:

1. the earliest 70% trains the model;
2. the following 15% chooses the review threshold;
3. the latest 15% is opened once for the reported test metrics.

This prevents a future transaction from leaking into the model used to score
the past. Because fraud is a rare event, PR-AUC is reported beside ROC-AUC,
precision, recall, F1, false-positive rate, and the confusion matrix.

Measured on 2026-08-31 with 50,000 generated transactions and seed 2026:

| Metric | Validation period | Held-out test period |
|---|---:|---:|
| Rows | 7,500 | 7,500 |
| Fraud prevalence | 1.81% | 1.87% |
| PR-AUC | 0.112 | 0.102 |
| ROC-AUC | 0.743 | 0.812 |
| Brier score | 0.0170 | 0.0179 |
| Precision at review threshold | 0.105 | 0.110 |
| Recall at review threshold | 0.301 | 0.450 |
| False-positive rate | 4.77% | 6.96% |

The calibrated review threshold is **0.055** and the block threshold is
**0.800**. The
test period deliberately comes later in time and contains mild distribution
shift. Its higher false-positive rate is visible rather than smoothed away.
Complete counts and reference histograms live in `artifacts/metadata.json`.

The current measured results are regenerated by:

```bash
make train
```

The in-process benchmark scores 5,000 generated requests at **0.951 ms p50**,
**1.187 ms p95**, and **1,009 scores/second** on this Windows host. These numbers
exclude HTTP and network time and are labelled that way in
`artifacts/benchmark.json`.

## Quick start

```bash
uv sync --extra dev
uv run python scripts/train.py --rows 50000
uv run uvicorn fraud_detection.api.main:app --reload --port 8000
```

Open <http://127.0.0.1:8000>. The service trains a small fallback model on
first boot if artifacts are absent, but reported measurements should always
come from the explicit training command above.

### Docker

```bash
docker compose up --build
```

The image trains a deterministic 30,000-row demonstration model during the
build, then serves it on port 8000.

## API

| Route | Purpose |
|---|---|
| `POST /api/score` | Validate and score a supplied transaction |
| `POST /api/simulate` | Generate and score dashboard demonstration traffic |
| `GET /api/recent` | Recent decisions and their strongest risk signals |
| `GET /api/stats` | Decision distribution, average risk, and drift status |
| `GET /api/drift` | Per-feature PSI values |
| `GET /api/model` | Thresholds, metrics, features, and dataset provenance |
| `POST /api/feedback` | Attach a confirmed outcome to a recent transaction |
| `GET /healthz` | Liveness, model version, and provenance |
| `GET /metrics` | Prometheus text format |

Interactive API documentation is available at <http://127.0.0.1:8000/docs>.

## Reproducing the demonstrations

```bash
make test       # unit and API tests; no network or paid service
make benchmark  # 5,000 in-process scores, writes artifacts/benchmark.json
```

With the API running, ordinary traffic followed by an intentional distribution
shift can be generated with:

```bash
uv run python scripts/simulate_live.py --normal 100 --suspicious 100
```

The second half sets new-device and foreign-transaction signals and raises
amounts. The test asserts that the same shift crosses the PSI alert threshold;
it does not merely trust the dashboard colour.

## Engineering choices

### A transparent baseline before a complex model

The deployed classifier is logistic regression with balanced class weights,
followed by Platt calibration on the validation period. Class balancing improves
the rare-event decision boundary but distorts raw probabilities; calibration is
why the API can call its output a probability rather than merely a ranking
score. For this portfolio system, exact local contributions, near-millisecond
model execution, and predictable persistence are more valuable than adding a
complex model before a real dataset establishes that it is needed.

### Thresholds are product policy

The model returns a probability. The validation period chooses a review
threshold under a maximum false-positive rate, and a separate higher threshold
blocks transactions. A payment company would set both from the economic cost
of missed fraud and customer friction; this repository keeps the policy visible
instead of treating `0.5` as a law of nature.

### Drift is not model accuracy

PSI says that recent inputs differ from the training reference. It does not say
that the model is wrong. Confirmed labels arriving later are required to measure
live precision and recall, which is why feedback is stored separately.

## Known limits

- Synthetic labels encode the generator's assumptions, so headline quality
  metrics are not externally valid.
- Recent transactions and feedback are in memory. A production deployment
  would use a durable event stream and database.
- The demonstration processes events through HTTP rather than Kafka/Redpanda.
  The model-serving boundary is real; the stream transport is deliberately
  kept out of the first version.
- The explanation is faithful to the linear model but is not a causal reason
  that a transaction is fraudulent.
- Retraining is an explicit command, not an automated production workflow.
